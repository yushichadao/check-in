# 班级签到系统

一套**可直接上传到服务器运行**的班级签到系统：运维端 / 管理端 / 用户端三端分离，
支持活动范围 + 服务端时间窗口校验、防代签、请假与补签的两级裁决、分级通知与邮件投递、
全量操作留痕（数据流审计）。

> **零配置即可运行**：不写任何配置文件，上传 → 安装依赖 → 启动即可用。
> 需要改端口 / 子路径 / 邮箱时，才在项目根目录放一个可选的 `.env`。

> **当前出厂状态**：账号名单已预置（未激活，无密码、无邮箱），业务数据为空。
> 全员需到 `/register.html` 完成邮箱验证并设置密码，登录后**必须先完成首次设置**才能进入系统。

> **配套资料**：官网宣传页（纯静态单页站点，可独立部署到任意静态托管）、三册图文说明书（用户端 / 管理端 / 运维端，含封面与页码）。

## 一、特性总览

- **三端分离**：运维端（运维隔离）/ 管理端（辅导员 → 小班主任 → 班委）/ 用户端（学生）。
- **双重校验**：活动范围（坐标系自适应）+ 服务端时间窗口，客户端时间不可信。
- **防代签**：账号首次签到绑定设备识别码；换设备放行但**留痕**（`device_change` 事件），管理端可核查。登录侧同账号至多「一台手机 + 一台电脑」。
- **请假 / 补签申诉**：支持图片材料、两级裁决（初审 / 终审）、裁决锁定与申诉复议、审核留言。
- **分级通知**：站内消息中心 + 邮件，按「是否在线活动」自动选择渠道；消息端分页。
- **数据流审计**：邮件 / 工单 / 申诉 / 账号 / 活动 / 登录等操作**无论谁触发都留痕**；
  管理端可看不可删，仅运维者可删；支持**中间部分加密（仅运维者可开关）**。
- **维护模式**：可排期、强制下线、服务端 503 拦截（前端删遮罩也无效）。
- **邮箱验证激活**：所有账号（含运维者）由上级预置后，本人须到注册页完成邮箱验证码验证并设置密码方可登录。
- **注册后必须完成首次设置**：设密后 `must_setup=1`，未完成前所有业务接口一律 `403 need_setup`。
- **无构建步骤**：纯原生 HTML / JS / CSS，前端全部资源（Leaflet、flatpickr、polygon-clipping、图标、样式）本地内置，不引用任何外网 CDN。
- **对外请求只有两处**（详见「十一、防作弊与定位 → 对外网络请求清单」）：地图**底图瓦片**、**邮件（SMTP，不配就没有）**。签到、范围判定、审批、站内消息全部在自有服务器内完成，不依赖外网。

## 二、快速开始

> **确定项目目录**：以下命令中的 `<项目目录>` 需替换为实际路径。
> ① **自动搜索**：在服务器终端依次尝试以下命令定位项目根目录：
> ```bash
> # 方式 A：按 package.json + 路径关键词搜索（推荐）
> find / -maxdepth 5 -name package.json -path "*/check-in/*" 2>/dev/null
> 
> # 方式 B：若已安装 mlocate / plocate（更快）
> locate check-in/package.json 2>/dev/null
> 
> # 验证：进入搜索结果目录，确认包含 server/ 和 tools/
> cd <搜索结果路径> && ls package.json server/index.js tools/setup-wizard.js
> ```
> ② **手动输入**：若您已知部署路径，直接使用该路径。
>    **目录格式**：绝对路径/项目名称，项目名称通常为 check-in，如：
>    - 宝塔默认：/www/wwwroot/<IP或域名>/check-in
>    - 自定义部署：/opt/check-in、/home/user/projects/check-in 等
>    输入后请验证：ls <项目目录>/package.json <项目目录>/server/index.js，两个文件均存在即为正确目录。

环境要求：**Node.js 20 及以上**（推荐 LTS 20 / 22），支持 **Linux** 和 **Windows**。
`better-sqlite3` 为原生 C++ 模块，切换平台或 Node 大版本后需重新编译——启动时会自动尝试 `npm rebuild`，也可手动执行 `npm ci`。macOS 无对应预编译产物，需本地 `npm ci` 重新拉取对应平台预编译（否则 `better-sqlite3` 无法加载）。


### 1. 本机运行

```bash
cd /path/to/check-in-demo   # ← 先切换到项目根目录（替换为实际路径）
npm ci                # 严格按 package-lock.json 安装；不要用 npm install（会漂移版本）
npm start             # 默认 http://localhost:3000/check-in/
```

首次启动会自动：创建数据目录与 SQLite 库 → 创建**初始运维者账号（未设密码）**。默认不预置活动范围，范围由运维者自行创建。

- 初始运维者账号**没有预置密码**：打开 `/register.html`，按「姓名 `运维者` + 身份 `运维者`」填写并获取邮箱验证码，
  完成邮箱验证、设置密码后即可以 `/ops.html` 登录。
- 忘记运维者密码：在服务器终端执行 `npm run reset-ops`，用打印出的新密码**直接登录**（会强制改密）。

- 登录后在运维端创建辅导员 / 小班主任 / 班委账号，以及预置学生账号；预置的账号同样由本人去 `/register.html` 激活。
- 新账号首次登录会被引导到 `/setup.html` 完成**通知偏好首次设置**后再进入系统。

### 2. 直接上传到服务器（推荐）

```bash
# ① 上传项目（node_modules 与 data 都无需上传；完整排除清单见第十四章）
rsync -avz --exclude node_modules --exclude data --exclude .env \
      --exclude '*.log' --exclude '*.out' --exclude '*.err' \
      ./ user@你的服务器:<项目目录>/

# ② 服务器上安装依赖并启动
cd <项目目录>
npm ci --omit=dev
npm start                       # 或 pm2 start server/index.js --name check-in
```

浏览器访问 `http://服务器IP:3000/check-in/` 即可（默认子路径为 `/check-in`，见第三章）。

- 数据目录、数据库、会话密钥都会在**首次启动时自动创建**，无需手工准备。
- 唯一需要人工处理的是**邮件功能**：注册 / 找回密码依赖邮箱验证码，**生产环境必须配置 SMTP**。
  未配置 SMTP 时：本地开发（`NODE_ENV != production`）会把邮件**逐封落盘**到 `data/mail-outbox/` 便于核对；
  **生产环境不落盘**（避免含验证码的邮件被静默写到磁盘，验证码类接口会直接返回 503）。
  联调 / 排障如需强制落盘，可在受控环境显式设置 `MAIL_OUTBOX=1`（落盘文件权限 `0600`，验证码类 15 分钟后自动清理）。

> 邮箱验证码（注册激活 `MAIL_REGISTER`、密码重置 `MAIL_PW_RESET`）必须依赖 SMTP；未配置 SMTP 时
> 注册激活与自助重置密码不可用，只能由管理员 / 运维者在后台「清除密码」后让本人重新设置。

## 三、配置：内置默认 + 可选 .env

所有配置都有**内置默认值**（集中在 `server/config.js` 的 `DEFAULTS`，以及 `server/mailtypes.js` 等），因此**不写 `.env` 也能完整运行**。
需要覆盖时，在项目根目录创建 `.env`（格式参考 `.env.example`），**环境变量优先级最高**，且 `.env` 不会被提交到仓库。

### 内置默认值

| 配置项 | 内置默认 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | 服务监听端口 |
| `NODE_ENV` | `production` | 运行环境 |
| `BASE_PATH` | `/check-in` | 部署子路径。**部署在域名根目录请设为空**（`BASE_PATH=`） |
| `TRUST_PROXY` | `1` | 位于 Nginx/Caddy 之后填 `1`；**直接对公网暴露 IP 必须填 `0`**（否则可伪造 X-Forwarded-For 绕过 IP 限流） |
| `COOKIE_SECURE` | `true` | 仅在请求为 TLS（`req.secure`）时才真正给 Cookie 加 `Secure` 标记；以纯 `http://IP:端口` 直连（未启用 HTTPS）时须设 `false`，否则登录失效 |
| `TOKEN_TTL` | `2h` | 会话令牌有效期 |
| `WO_TIMEOUT_HOURS` | `48` | 权限工单超时自动驳回（小时） |
| `DB_DIR` | 空（解析为 `./data`） | 数据库与密钥文件目录（可指向加密卷） |
| `JWT_SECRET` | 自动生成 | 未设置时自动生成并持久化到 `data/.jwt-secret` |
| `DATAFLOW_KEY` | 回落 `JWT_SECRET` | 数据流中间部分加密密钥（由 `server/datalog.js` 读取；更改后旧密文将无法解密） |
| `GROUP_NAME` | 空（**必填**） | **② 班级名称**，如 `通信工程2607班`。留空则运维者无法登录（403）、注册发码被拦截（503），须先用 `npm run config` 配置 |
| `SYSTEM_NAME` | 自动拼接 | **③ 系统全称**，本班这套系统的完整称呼。**留空时自动拼接为「班级名 + 商品名」**（如 `通信工程2607班签到系统`）；班级名已含商品名或以「系统」结尾时不重复拼接。用于浏览器标签标题、关于页「系统名称」、邮件正文系统名 |
| `OPS_NAME` | `运维者` | 初始运维者姓名（**仅首次建库时生效**；运维者**不预置密码**，须注册激活） |
| `SMTP_*` | 空 | 邮件配置；**生产环境必须填写**（不填则验证码类接口返回 503，且不把邮件落盘） |
| `FENCE_MAX_ACCURACY` | `200` | 允许的最大定位误差（米），精度差于此值直接拒绝签到 |
| `MAIL_SYSTEM_NAME` | `SYSTEM_NAME` | 邮件正文中的系统名（可选；默认取系统全称） |

> **三层命名不要混用**：① **商品名（品牌）= `班级签到系统`**，代码固定，任何端不可改（邮件落款用它）；
> ② **班级名 = `GROUP_NAME`**，运维者配置；③ **系统全称 = `SYSTEM_NAME`**，由 ② + ① 派生或直接指定。
> 注：本系统不提供「发件显示名」配置项（SMTP 发件人显示名固定为品牌，不随 ③ 变化）。
> 如需让收件端显示别的名称，请到发件邮箱服务商修改该邮箱的账户名称 / 昵称；是否生效取决于服务商，属服务商侧行为。

| `SMTP_PASS` | 空 | 发信授权码（非登录密码）。**终端里明文显示便于核对，但写入 `.env` 时自动加密**（`enc:v1:…`）；也可直接填明文，两种都支持 |
| `SECRET_KEY` | 自动生成 | 授权码加密密钥；未设置时使用 `data/.secret-key`（自动生成，权限 0600）。**迁移服务器必须连该文件一起复制**，否则授权码需重新填写 |

> 其余邮件细节（`MAIL_FROM` / `MAIL_SUBJECT` / `MAIL_TEXT`）均可选；`SMTP_SECURE` 默认 `true`（465 端口），587 端口请改 `false`（STARTTLS）。

> **TUI 的输入边界**：`npm run config` **不是命令行，也不接入任何 AI**。
> 它只接受「菜单编号 / 配置值 / Y / N」，读到的每一行都不会交给 shell 执行、也不会转发给任何模型；
> 服务器命令（`ls`、`rm`、`npm`…）、shell 元字符、`@` 与 `/` 开头的指令、自然语言会被直接拒绝，且不写入 `.env`。
> 请在服务器终端直接运行它，不要挂在 AI 代理或自动化工具之下。
>
> **TUI 自动化能力**（保存配置后自动执行，无需手动操作）：
> - **Nginx 反向代理**：通过 `nginx -T` 获取完整配置（含 include 展开），自动检测/修复/添加 `location ^~` 反代；优先写入 HTTPS server 块；权限不足或配置异常时降级为可复制的配置指令
> - **HTTPS 证书检测**：自动扫描 SSL 证书文件并检查有效期
> - **SMTP 连通性预检**：填写授权码后立即验证 SMTP 连接是否可用
> - **服务启动/重启**：服务未运行时主动询问是否启动（优先 PM2，无 PM2 则 detached spawn）；已运行时自动识别 PM2 / systemd / supervisor / Docker / Podman / forever / OpenRC / 宝塔 / 1Panel 等 13 种托管环境并执行对应重启命令
> - **URL 预览**：选择部署位置后立即显示完整访问链接（域名 + IP，根据 HTTPS 设置自动切换协议）
> - **端口智能推荐**：端口被占用时自动扫描 3000-4000 寻找空闲端口
> - **`.env` 自动备份**：每次保存前自动创建 `.env.bak`
> - **配置变更 diff**：保存确认时显示旧值 → 新值对比
> - **数据库重置保护**：一键初始化前显示当前数据量统计（用户/活动/签到记录数）
> - **日志查看**：菜单第 7 项可直接查看最近 30 行服务日志

### 首次部署建议修改的项

```ini
# .env（示例，全部可省略）
TRUST_PROXY=1                   # 挂 Nginx 后填 1
COOKIE_SECURE=true              # 启用 HTTPS 后填 true
JWT_SECRET=<48 字节随机串>       # 可选，留空则自动生成并持久化
DATAFLOW_KEY=<32 字节随机串>     # 可选，改动后旧密文将无法解密
OPS_NAME=运维者                  # 仅首次建库生效

# —— 三层命名：① 商品名（品牌，代码固定不可改）· ② 班级名 · ③ 系统全称 ——
GROUP_NAME=你的班级名                # ② 必填，无默认值；例：通信工程2607班
#SYSTEM_NAME=                     # ③ 留空＝自动拼接「班级名＋商品名」

SMTP_HOST=smtp.qq.com           # 邮件（可选，生产必填）
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=你的邮箱@qq.com
SMTP_PASS=邮箱授权码             # 注意是「授权码」，而不是登录密码
# 只填发件地址即可；发件显示名取自发件邮箱在服务商处登记的账户名称，需到邮箱服务商修改
MAIL_FROM=no-reply@你的域名
```

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

> 邮件服务商参考（TUI 内置 13 种预设，也可手动填写）：QQ、163、腾讯企业邮、阿里云邮箱、新浪、搜狐、移动 139、电信 189、Gmail、Outlook/Hotmail、Yahoo、iCloud、其他/自建。
> TUI 会根据填写的发信邮箱域名**自动识别服务商**并切换 SMTP 配置；587 端口请设 `SMTP_SECURE=false`（STARTTLS）。
> 设置 `MAIL_OUTBOX=1` 可在已配置 SMTP 的情况下**强制只落盘不真发**（联调 / 排障用，受控环境专用）；
> 落盘文件权限 `0600`，验证码类邮件 15 分钟后自动清理。

## 四、账号、角色与权限

| 角色 | 层级 | 说明 | 登录字段 | 入口 |
| --- | --- | --- | --- | --- |
| 运维者 | L9 | 运维隔离，全局通配，不参与业务授权 | 姓名 + 身份 + 密码 | `/ops.html` |
| 辅导员 | L3 | 最高业务层级：终审、工单审批、定位核验开关、隐私告知 | 姓名 + 身份 + 密码 | `/manager.html` |
| 小班主任 | L2 | 终审 / 覆盖、向下授权、账号管理、系统设置 | 姓名 + 身份 + 密码 | `/manager.html` |
| 班委 | L1 | 画活动范围、建活动、看明细、初步裁决（原「班长 / 学委」已合并为「班委」） | 姓名 + 身份 + 密码 | `/manager.html` |
| 普通学生 | L0 | 仅能签到、申诉、查看本人数据 | 姓名 + 学号 + 身份 + 密码 | `/user.html` |

- 学号不再限制格式：学生可填写任意学号（如工号、自定义编号等），无需遵循固定模板；管理员 / 运维者学号可留空。
- 同一人可同时拥有管理账号与普通账号。
- **所有账号均不预置密码**：由上级在运维端 / 管理端预置（登记姓名、学号、身份）后，本人到 `/register.html` 完成邮箱验证码验证并设置密码方可登录。

### 权限获取双轨制

- **角色基线**：层级达到权限码 `min` 即天然持有（不可撤回）。如班委天然可画活动范围、建活动、初步裁决。
- **高危权限**：超出自身基线的高危权限，需提交**权限工单**（可勾选 1~N 位上级审批），
  或由上级**向下授权**主动下放；两者都会写入 `permission_grants` 并邮件通知。
- **账号管理范围（Scope）**：每个管理号只能管理 `account_scopes` 中绑定的账号（运维者为全局通配）。
  账号管理、向下授权、数据查看、工单审批四类操作全部受此约束。

### 活动范围（核验）权限模型

活动范围即原「电子围栏」，已更名：

- 「画 / 改 / 删活动范围」「地图查看活动范围」「把活动范围绑定到活动」均为**管理员基线能力**（`FENCE_DRAW` / `FENCE_VIEW_MAP` 及活动绑定，`min=1`）：运维者与管理端角色天然可操作，**无需单独权限**。
- 「启动活动范围核验 / 让用户端上传定位」才是真正的**权限**（`FENCE_VERIFY`，高危）：基线**仅辅导员（R3）及以上（含运维者）**可行使；
  绑定了活动范围的活动，是否实际启用「定位上传核验」取决于该权限 + 定位核验总开关（开不开启是另一回事）。
- 当班级**缺辅导员**时，该权限由「自动代管」下放至小班主任 / 班委（见第二十一章）；上级一注册到岗即自动收回。
- **定位核验门控**：需同时满足「持有 `FENCE_VERIFY`」+「定位核验总开关已开启」。
  开关需持有 `FENCE_VERIFY` 方可切换；关闭时前端隐藏定位控件、后端拒绝位置上传。

### 密码强度规则

所有设密入口（首次激活设置、修改密码、邮箱验证码重置）统一校验：**至少 6 位，且必须同时包含字母和数字**。
弱密码（纯数字、纯字母、过短）会被服务端拒绝并提示。

## 五、注册激活与首次设置

### 1. 账号预置 + 自主注册（邮箱验证激活）

1. 运维端 / 管理端先**预置**账号（登记姓名、学号、身份），此时**无密码**，账号处于「未激活」状态。
2. 本人在 `/register.html` 填写相同信息，系统下发**邮箱验证码**（`MAIL_REGISTER`）到本人邮箱，验证通过后设置密码。
   - 信息不一致无法注册成功，避免任意注册；且**必须先完整阅读《隐私政策》**（见第九章）。
   - 邮箱验证码有效期 10 分钟，重发间隔 60 秒，最多尝试 5 次。
   - 邮箱为**必填项**：未通过邮箱验证的账号不能登录。
3. 设置密码成功即激活，系统标记该账号 `must_setup=1`。

### 2. 注册后必须先完成首次设置

- 设密（含管理员「清除密码」后重设、重启用后重设）后，账号只能停留在 `/setup.html` 完成**通知偏好**设置；
- 在此之前，服务端对所有业务接口一律返回 `403 need_setup`，**换 URL 直接进其它页面也无效**；
- 白名单仅放行 `me` / `logout` / `ping` / `complete-setup` / 通知偏好接口；
- 完成之后随时可在「个人信息 → 通知偏好」修改。

首次设置页会按登录身份呈现不同内容：

- **学生端（普通学生）**：除通知偏好外，额外提供「定位上传授权」选择——可「自愿授权」或「暂不授权」；不授权也能正常签到，授权状态属个人隐私且不写入数据流。
- **管理端（班委 / 小班主任 / 辅导员）**：通知偏好只展示管理端实际能收到的 2 项（退回 / 回执 / 请假补签结果为普通学生专属，不在管理端展示）；并提示班级级开关（如定位核验、系统安全）请进入系统后在「通知设置」「系统安全」中配置。
- **运维端**：除通知偏好外，提供两项运维开关——「数据流隐私打码」（列表内姓名 / 学号中间打码）与「自动代管」（缺上级时由下一级在岗管理岗代行其基线权力）；两者均仅运维者可改，且均默认开启。

### 3. 找回密码

- **普通账号 / 管理账号**：管理员 / 运维者在「密码清除」中选中账号执行**清除密码**——**看不到原密码**；原密码立即失效，本人回到注册页重新设置密码后方可登录（此时 `must_change_pwd=1`）。
- **运维者账号**：服务器终端执行 `npm run reset-ops` 重置（标记已验证后走注册流程设密）。
- **邮箱验证码自助重置**：已配置 SMTP 时，用户在登录页「忘记密码」提交申请，邮箱收 `MAIL_PW_RESET` 验证码后自助重置。
- **已注销账号恢复**：提交「重启用」工单（`REACTIVATE`），上级审批通过后清空密码回到未激活，本人重新注册设密。

## 七、通知与邮件投递规则

系统按「收件人是否**正在使用**系统」自动选择渠道：

| 情况 | 判定依据 | 投递方式 |
| --- | --- | --- |
| 任意设备**在线且活动** | 有在线会话，且最近 **2 分钟**内有心跳（页面每 20s 轮询、每 2 分钟心跳） | **仅站内消息端**（实时弹 toast） |
| 全部离线，或在线但**不活动** | 超过 2 分钟无心跳，或没有在线会话 | **站内消息端 + 邮件 都发** |
| **内置必邮**类型 | 硬编码，不受偏好开关影响 | **只发邮件**，不写站内 |

- **内置必邮（不可配置）**：注册激活验证码 `MAIL_REGISTER`、密码重置验证码 `MAIL_PW_RESET`、运维告警 `MAIL_OPS_ALERT`。
- 消息中心（铃铛）支持**分页**，分层展示紧急 / 通知 / 普通消息；打开即自动标记已读。
- 投递结果（渠道为 `inbox` / `email` / `both` / `none`）**都会写入数据流留痕**。
- 通知偏好按内容类型分层配置，`mandatory=true` 的必提醒在界面上置灰、**不可取消**。

### 通知偏好按角色可见性（角色过滤）

通知偏好的「可选项」会随登录身份而不同，避免出现「设了却永远收不到」的无效配置：

- **学生端（普通学生）**：可见全部 **12** 项（活动与签到类 8 项 + 退回 + 回执（含请假 / 补签审核结果）+ 工单回复 + 系统消息）。
- **管理端 / 运维端**：仅可见 **2** 项——`NT_WO_REPLY` 工单回复提醒、`NT_SYS_MSG` 系统消息（退回 / 回执为普通学生专属，不在管理端 / 运维端展示）。

理由：活动与签到类提醒（活动创建、签到开始、各倒计时、活动开始、缺勤等）的收件人**恒为普通学生**，管理端 / 运维端收不到，故其偏好面板中直接隐藏这 8 项；必提醒（如工单回复、系统消息）对所有角色均置灰不可关闭。

### 个人通知渠道偏好（自服务开关）

除管理员层的「内容类型总开关」外，每位账号还能在「个人信息 → 通知偏好」里**自选自用渠道**（新账号在 `/setup.html` 首次设置）：

| 渠道 | 含义 | 适用 |
| --- | --- | --- |
| `站内 + 邮件`（默认） | 离线 / 不活动时站内消息与邮件都发 | 全部类型（默认） |
| `仅站内消息` | 只在消息中心提醒，不发邮件 | 活动 / 签到提醒、退回 / 回执等可选类 |
| `关闭` | 完全不接收 | 同上（必提醒与安全类不可关闭） |

- **强制保留（不可关闭）**：密码重置验证码、密码变更 / 异地登录等安全邮件、工单与系统消息（`NT_WO_REPLY` / `NT_SYS_MSG`）始终按系统规则送达。
- 数据落在 `user_notify_pref` 表（`user_id + kind` 唯一）；选回默认 `站内 + 邮件` 即删除该行。

### 邮件类型清单

所有邮件类型**只在 `server/mailtypes.js` 登记一次**（类型码 / 中文名 / 分组 / 收件人 / 触发时机），
邮件内容由 `server/notify.js` 的 `build*` 函数统一拼装，发送时按类型码留痕与落盘；

| 密码与安全 | `MAIL_REGISTER` / `MAIL_PW_RESET` | 账号激活验证码 / 密码重置验证码 | 本人邮箱（必邮） |

### 内部工单（权限申请 / 信息修改·反馈 / 重启用）

工单分三类：`perm` 权限申请（审批通过即自动授权）、`info` 信息修改 / 反馈（由上级人工处理）、`reactivate` 重启用（恢复已注销账号）。

| 环节 | 收件人 | 方式 |
| --- | --- | --- |
| 提交工单 | 申请人勾选的**每一位处理人** | 站内必达；离线 / 不活动时**加发邮件** `MAIL_WO_SUBMITTED` |
| 提交工单 | 申请人自己 | 站内回执；离线时加发邮件回执 `MAIL_RECEIPT` |
| 审批结果 | 申请人 | 站内 + 邮件 `MAIL_WO_APPROVED` / `MAIL_WO_REJECTED`（`info` 类走 `MAIL_RECEIPT`） |
| 待办催办（挂起 > 30 分钟） | 处理人 | 在线仅站内；离线 / 不活动 站内 + 邮件 `MAIL_WO_REMINDER` |
| 超时关闭（> `WO_TIMEOUT_HOURS` 小时） | 申请人（邮件 `MAIL_WO_TIMEOUT`）+ 各处理人（站内） | 自动执行 |

- **处理人必须能真正处理工单**：候选列表与提交校验都要求「层级更高 + 申请人在其管理范围内 + 持有 `AUTH_APPROVE_WO`（或为运维者）」。
- **可见对象**：处理人始终可见；运维者可见全部；持有 `AUTH_APPROVE_WO` 且在管理范围内可见待审批 + 自己处理过的；其余账号不可见（引导提交权限工单）。
- 提交人对自己的工单始终可见（`/mine`）。

## 八、数据流（审计留痕）

**留痕范围**：邮件发送、通知投递、权限工单、申诉（含回复）、账号操作、活动、活动范围、签到、登录、系统设置等——
**无论由谁操作，都记录「操作者 / 动作 / 目标 / 摘要 / 投递渠道 / 时间」**；系统自动触发时操作者记为「系统」。

**查看与权限**

| 能力 | 要求 |
| --- | --- |
| 查看列表 / 只读详情 | 运维者通配，或持有 `VIEW_DATAFLOW`（R2+） |
| **另开页面查看只读详情** | `public/dataflow.html?id=<记录ID>`（管理端 / 开发端均有入口按钮） |
| 删除记录 | **仅运维者**（管理端返回 403，禁止删除） |
| 切换「中间部分加密」 | 仅运维者 |

**筛选**：列表支持分类、关键词、**操作者**、**时间范围**，并支持分页。

**中间部分加密（仅运维者可开关）**
- 开启后，写入 `data_flow` 时对 `target` / `detail` 的**中间段做 AES-256-GCM 加密**（密钥来自 `DATAFLOW_KEY`，回落 `JWT_SECRET`），
  **首尾各留少量明文**并以 `⟪…⟫` 标记，既能区分记录又可保护敏感内容。
- 运维者查看详情时可点击解密还原；关闭开关后新记录恢复明文。

## 十、维护模式

- **排期**：运维端设置起止时间与说明 → 到开始时间由调度器**自动进入维护**（也可「立即进入维护」）。
- **进入维护时**：除运维端外的在线账号被**强制下线**（会话挂起，不销毁）；
  全站显示「系统更新维护中」遮罩并展示起止时间。
- **服务端强制拦截**：维护中除运维端外，所有 `/api` 请求返回 `503`
  （仅放行 `me` / `login` / `logout` / `privacy` / `settings-public`），**用 F12 删掉前端遮罩也无法继续操作**。
- **结束**：只能由运维端手动结束；结束后清除挂起，**原在线账号自动恢复上线**（无需重新登录）。
- **开启前预告**：已排期且开始前 10 分钟内，前端弹出「系统维护预告」。
- **活动禁排**：维护窗口**前后各 1 小时禁止创建活动**，冲突返回 403。
- 在线人数不限。

## 十一、防作弊与定位

- **定位仅用于范围记录**：仅在「活动范围核验」开启、**且本人已自愿授权**时才采集定位；
  判定所需的经纬度与定位精度会保存在 `checkins` 表以供复核；
  界面默认只展示「活动范围内 / 活动范围外」的结论，仅持有「查看学生定位」权限、且运维者已开启相应查看开关的管理员可以在地图上查看，查看行为同样留痕。
  未开启核验或本人未授权时**不采集任何位置**。
- **上传定位会记入数据流**：本人已授权并实际上传定位的签到，数据流中会标注「（含定位上传）」；但「是否授权」本身属隐私，不写入数据流。
- **用户端另有「前台连续定位」**：学生打开「查看活动范围」地图时会自动 `watchPosition` 把自己的位置刷到地图上，**纯本地显示、不上传服务端、不需要授权、也不受定位核验总开关限制**，关闭地图即 `clearWatch` 释放；这不属于后台追踪。
- **防代签**：账号首次签到绑定设备识别码；换设备**放行但留痕**（记录 `device_change` 事件并更新绑定），管理端可核查，不做硬性拒绝以免误伤正常换机。
- **防离线 / 篡改**：签到时间窗口与活动范围判定全部在服务端用服务器时间计算，不信任客户端。
- **活动范围定位核验（防严重偏移）**：
  - 自动兼容坐标系：同时用「设备原始坐标」「WGS-84→GCJ-02」「GCJ-02→WGS-84」三种结果比对活动范围，任一命中即判定在内；
  - 严格边界：按管理员绘制的活动范围边界判定，不叠加定位精度补偿（缓冲由管理员画范围时主动往外预留）；
  - 精度兜底：定位精度差于 200 米（`FENCE_MAX_ACCURACY`）直接拒绝签到并要求重新定位；
  - 仍保留人工校准：活动范围表 `offset_lng` / `offset_lat` 用于整体偏移微调。

### 对外网络请求清单

浏览器侧会向外部发请求的只有下面两处：

| # | 触发时机 | 目标 | 是否可关 / 可换 |
| --- | --- | --- | --- |
| 1 | 打开活动范围地图、查看学生定位、管理端给目的地打点 | 在线地图**底图瓦片**：默认高德 `wprd0{1-4}.is.autonavi.com` / `webst0{1-4}.is.autonavi.com`（境内、无需密钥） | 不可关（不联网则地图区域空白，功能不受影响）；可自行在 `public/js/fence-editor.js`、`manager.js`、`ops.js` 中把 `TILE_*` / `DEST_TILE` 换成自备瓦片服务 |
| 2 | 发送验证码、邮件通知 | 你配置的 **SMTP 服务器**（第三方或自建） | 可关：不配 `SMTP_*` 时全部通知走站内消息，仅验证码类接口返回 503 |

补充说明：

- **前端库全部本地内置**：`public/vendor/`（Leaflet、flatpickr、polygon-clipping 等）+ `public/css/`、`public/js/`，不引用任何外网 CDN；`theme.css` 也已移除原先指向 `fonts.googleapis.com` 的 `@import`，标题字体改用本地系统字体栈。
- **定位（Geolocation）**：由浏览器 / 手机系统提供，联网时可用 WiFi、基站辅助，精度更高——这是终端机制，不属于本系统发起的请求；系统只把坐标随签到一起上传到自有服务器，不发往第三方。
- **地图底图与业务数据分离**：底图请求只包含瓦片编号（`z/x/y`）与来源标识，不携带学生姓名、学号或签到内容。
- 想确认还有没有别的外部请求，断网跑一遍就知道：除了地图区域是空白的，签到、审批、通知、审计都还能用。

## 十四、部署到服务器

### 1. 上传文件清单与命令

**要上传（项目源码与必要文件）**

```
server/         后端全部代码
public/         前端页面与静态资源
package.json    package-lock.json   .npmrc   依赖清单（服务器上按它装依赖）
.env.example    配置示例（复制到 .env 后填写）
.gitignore / README.md / start.bat  可选
```

**不要上传（含密钥 / 运行时数据 / 体积大）**

```
node_modules/   依赖目录（服务器 npm ci 重新安装）
data/           运行时数据库、密钥、上传图片（首次启动自动创建，切勿带走旧库）
.env            含 JWT_SECRET / 授权码等密钥，切勿上传或提交
*.log *.out *.err  日志
```

**上传命令（排除依赖 / 数据 / 密钥 / 日志）**

```bash
rsync -avz --exclude node_modules --exclude data --exclude .env \
      --exclude '*.log' --exclude '*.out' --exclude '*.err' \
      ./ user@你的服务器:<项目目录>/
```

> `.env` **不随 rsync 上传**（含密钥，且已 gitignore）。两种填法：
> - **推荐**：本地 `.env` 若已配好，直接安全传过去：
>   `scp .env user@你的服务器:<项目目录>/.env`（密钥走 scp，不进仓库/不随代码）。
> - 或在服务器现编：`cp .env.example .env && nano .env` 后按第三章填写。

### 2. 服务器上安装与启动

```bash
cd <项目目录>

# 锁定 npm 行为（必须）：防止 npm install 漂移版本——better-sqlite3 等原生模块
# 与 Node ABI 强绑定，漂移后会在运行时段错误崩溃（PM2 errored / 访问 502）
echo "save-exact=true" > <项目目录>/.npmrc

npm ci --omit=dev          # 严格按 package-lock.json 安装生产依赖
```

> **更新应用时一律用 `npm ci`，不要用 `npm install`**（后者会重新解析版本，可能把
> `better-sqlite3` 从 12.11.1 漂移到 13.x 而与 Node 的 ABI 不兼容）。
> 若 `node_modules` 被面板 / 定时任务 / 其它脚本覆盖过：`rm -rf node_modules && npm ci`；
> 启动前可先跑 `npm run verify:deps`。
>
> 仓库根目录已内置 `.npmrc`（`save-exact=true` + `package-lock=true`），rsync 会一并上传；
> 上面的 `echo` 是兜底：手工拷文件遗漏、或该文件被清理时重建它。
> 即便漏做，服务启动时也会**自动检测并尝试修复**（见第十七章）。

```bash
# 方式一：pm2（推荐）
npm i -g pm2
pm2 start server/index.js --name check-in
pm2 save && pm2 startup

# 方式二：systemd（ExecStart=/usr/bin/node <项目目录>/server/index.js）
# 方式三：Windows 双击 start.bat
```

### 3. 以子路径部署（默认，`https://域名/check-in`）

设置 `BASE_PATH=/check-in`（内置默认值）后，服务会自动把页面、静态资源与接口都挂到该前缀下。
TUI 配置向导支持选择 `/check-in`、`/checkin` 或**自定义子路径**（如 `/office/sign`），选择后立即显示完整访问 URL 预览，并通过 `nginx -T` 自动检测/修复/添加 `location ^~` 反向代理配置（失败时输出可复制的配置块）。
前端资源与接口均使用相对路径，**无需改动任何前端代码**。Nginx：

```nginx
location /check-in/ {
  proxy_pass http://127.0.0.1:3000/check-in/;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
location = /check-in { return 302 /check-in/; }   # 自动补斜杠
```

### 4. HTTPS（强烈建议，签到定位的前置条件）

浏览器**只在「安全上下文」（HTTPS 或 localhost）下开放定位能力**，因此手机端要定位签到，**必须走 HTTPS**。本系统两种启用方式任选其一：

**方式 A：Node 内置 HTTPS（零额外组件，推荐本地 / 单机部署）**

配置证书与私钥路径即自动启用 HTTPS 监听（与原有 HTTP 并存）：

```bash
# .env
SSL_CERT=/path/to/fullchain.pem
SSL_KEY=/path/to/privkey.pem
HTTPS_PORT=3443            # 可选，默认 3443（避开 443 以免需 root）
# HTTPS_ONLY=true          # 可选：仅 HTTPS，关闭 HTTP 监听
# REDIRECT_HTTP_TO_HTTPS=true  # 可选：保留 HTTP 但 301 跳转到 HTTPS
```

- 本地 / 局域网测试可用自签证书（含本机局域网 IP），生成后将 `cert.pem` 安装为手机**信任的根证书**即可（iOS：安装描述文件后到「证书信任设置」启用完全信任；Android：改后缀 `.crt` 后「从存储设备安装」）。TUI 配置向导在启用 HTTPS 时会自动检测已有 SSL 证书及有效期。

- 启用 `HTTPS_ONLY` 或 `REDIR` 时，登录 Cookie 会自动标记为 `Secure`，无需再手工设 `COOKIE_SECURE`。

**方式 B：放在 Nginx / Caddy 反代之后（生产推荐）**

```nginx
server {
  listen 443 ssl;
  server_name 你的域名;
  ssl_certificate     /etc/letsencrypt/live/你的域名/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/你的域名/privkey.pem;

  location = /          { return 302 /check-in/; }
  location = /check-in { return 302 /check-in/; }

  location /check-in/ {
    proxy_pass http://127.0.0.1:3000/check-in/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

> 部署在**域名根目录**时，把 `BASE_PATH=` 设为空，并把上面的 `location /check-in/` 改为 `location /`。
> **切勿为 `.css` / `.js` / 图片单独加本地静态块**：所有前端资源都随 `/check-in/` 由 Node 提供，
> 另写 `location ~* \.(css|js|png)$ { root ...; }` 之类会出现「页面能开、但样式 / 脚本 404」。
> 申请证书：`certbot --nginx -d 你的域名`。

**启用 HTTPS 后**：若用反代方式，把 `.env` 的 `COOKIE_SECURE=true`、`TRUST_PROXY=1`；用方式 A 且开启了 `HTTPS_ONLY`/`REDIRECT_HTTP_TO_HTTPS` 则 Cookie Secure 已自动处理。

### 6. 运行时文件位置（data/ 目录）

所有运行期产生的文件都落在 **`DATA_DIR`**，默认是项目内的 `./data`（即部署目录下的 `data/`）。
位置由 `.env` 的 `DB_DIR` 决定：留空 = 内置默认 `./data`；填绝对路径（如 `/var/lib/checkin/data`）= 放到该处（适合指向加密卷）。

**上传时 `data/` 一定不能传**（运行时自动生成，且会带本地旧库 / 旧密钥）；服务器应「首次启动自动建空库」。

| 文件 / 目录 | 何时产生 |
| --- | --- |
| `app.db`（可能带 `app.db-wal` / `app.db-shm`） | 首次启动自动建库 |
| `.jwt-secret` | **仅当 `.env` 未设 `JWT_SECRET`** 时自动生成并持久化 |
| `uploads/YYYYMM/...` | 用户上传的申诉 / 佐证图片（服务器重命名带时间戳） |
| `mail-outbox/*.html` | 仅非生产环境或显式 `MAIL_OUTBOX=1` 时落盘（权限 `0600`，验证码类 15 分钟后清理） |
| `mail-preview/` | 仅执行 `npm run mail:preview` 时生成 |
| `backups/` | 执行出厂重置时的自动备份 |

> 应用**不写任何 `*.log` 到磁盘**：日志只输出到 `console.log`（由 pm2 / Nginx 接管）。

## 十五、备份、迁移与恢复出厂设置

- **简单备份**：定期拷贝 `data/app.db`（若存在 `-wal` / `-shm`，请先停止服务再拷）。
  同时备份 `data/.jwt-secret`（或 `.env` 中的 `JWT_SECRET`）与 `DATAFLOW_KEY`——
  丢失密钥将导致数据流旧密文无法解密。
- **目录整体迁移**：整包拷贝 `data/` 目录即可（需保持服务停止状态）。
- **恢复出厂设置**：`npm run factory-reset`
  - **保留**：全部账号（重置为未激活：清空密码与邮箱、`email_verified=0`、`must_setup=1`）、
    `settings` 中的迁移标记、以及 `.env` 里的 SMTP 发件邮箱配置（不在数据库内）；
  - **清空**：活动 / 签到 / 活动范围 / 请假 / 补签 / 工单 / 授权 / 通知 / 会话 / 数据流 / 偏好等全部业务数据；
  - **清理**：`data/uploads`、`data/mail-preview`、`data/mail-outbox` 中的测试附件与落盘邮件；
  - **备份**：执行前自动备份到 `data/backups/factory-reset-backup-<时间戳>-app.db*`；
  - 之后重启服务即可，所有人重新注册激活（并强制完成首次设置）。
- 出厂重置后，启动**不会**再把默认活动范围补回来——范围交由运维者自行创建。

> 关于「加密数据库目录」：服务端是普通 Node 进程，对 `DB_DIR` 拥有与运行账号相同的读写权限，
> 会在启动时递归创建目录并写删探针文件验证可读写。
> 推荐用**磁盘 / 文件系统级加密**（BitLocker / LUKS / fscrypt）后把 `DB_DIR` 指向加密卷内目录——
> 对应用完全透明，性能损耗极小。

## 十六、安全加固

**系统已内置**
- 服务端：Helmet 安全头、请求体体积上限、全量参数化 SQL、bcrypt 密码哈希、
  Cookie `HttpOnly` + `SameSite`、登录失败锁定与统一错误文案（防枚举）、
  **分层限流**（全局 300/分钟；登录 60/15 分钟；验证码 10/10 分钟）、
  **跨站写操作 Origin 校验（CSRF）**、慢连接超时、**维护模式服务端拦截**、
  **首次设置强制门控**（未完成设置前业务接口一律 403）。
- 前端：`api.js` 内置维护遮罩守卫与 `need_setup` 自动跳转；权限门控组件统一灰度 / 锁定样式。

**建议追加**
- Nginx 层再兜一层：`limit_req` / `limit_conn` 限速限并发、只暴露 443、3000 端口不对外开放、开启 HSTS。
- `TRUST_PROXY` 与部署形态严格匹配：直连设 `0`，位于反代之后设 `1`。
- 数据目录权限最小化：仅服务运行账号可读可写。
- 服务器 `node_modules` 不要被面板 / 同步工具覆盖（见第十七章）。

## 十七、依赖自检与自动修复（better-sqlite3）

`better-sqlite3` 是**原生模块**，与 Node 的 ABI 强绑定。版本被漂移（如 12.11.1 → 13.x）时，
`require` 会**段错误（SIGSEGV）直接崩溃**——try/catch 抓不到，进程日志几乎没有内容，
表现为 PM2 errored + nginx 502。

`server/deps-check.js` 在**加载任何原生模块之前**执行，判断准则是「能不能安全加载」：

1. 读取已安装版本与二进制产物（不加载模块）；
2. 在**子进程**里 `require` 一次做冒烟（子进程崩了主进程仍能给出可读错误）；
3. 未安装或加载失败 → **自动修复**：`npm install better-sqlite3@<锁定版本> --save-exact` → `npm rebuild better-sqlite3`，每步立即复验；
4. 修复带进程锁（`.deps-fix.lock`，10 分钟内不重复，避免重启风暴里并发跑 npm）；
5. **只有修复后依然加载不了**才终止启动并打印可直接照做的修复命令；仅「版本不一致但能正常加载」时告警放行。

| 环境变量 | 作用 |
| --- | --- |
| `SKIP_DEP_CHECK=1` | 完全跳过自检（仅调试用） |
| `SKIP_DEP_SMOKE=1` | 只跳过子进程冒烟 |
| `DEP_AUTO_FIX=0` | 关闭自动修复，只报告 |
| `DEP_AUTO_FIX=align` | 版本与 `package.json` 不一致时也自动对齐 |
| `DEP_AUTO_FIX=ci` | 同上，且兜底执行 `npm ci` |

排查「反复被覆盖」的来源：宝塔「Node 项目」安装依赖按钮、IDE / SFTP 同步 `node_modules`、
部署脚本里的 `npm install`（一律改 `npm ci`）、其它面板 / 定时任务 / CI 触碰该目录。

## 十九、常见问题

**Q：一定要写 `.env` 吗？**
不需要。内置默认值即可运行；`.env` 只用于覆盖（改端口、子路径、密钥、邮箱等）。

**Q：上传后访问 404？**
默认部署在子路径 `/check-in`。若你部署在根目录，请设置 `BASE_PATH=`（空）。

**Q：登录后立刻掉线 / 登录失效？**
多为 `COOKIE_SECURE` 与访问方式不匹配：以 `http://IP:端口` 访问时必须为 `false`；启用 HTTPS 后才设为 `true`。

**Q：IP 限流形同虚设 / 日志里 IP 不对？**
`TRUST_PROXY` 与部署形态不匹配。直连公网设 `0`，在 Nginx 后设 `1`。

**Q：邮件发不出去？**
生产环境**必须配置 SMTP**（注册 / 找回密码依赖邮箱验证码）；未配置时验证码类接口返回 503，且不会把含验证码的邮件落盘。
注意 `SMTP_PASS` 填的是**授权码**而非邮箱登录密码。

**Q：注册后一直停在「首次设置」页？**
这是预期行为：设密后必须先完成通知偏好设置，服务端会把所有业务接口拦成 `403 need_setup`。完成设置后即可正常使用。

**Q：管理端看不到学生上传的图片？**
确认工单 / 申诉详情已展开（可查看图文并回复）；附件绑定见 `appeal_attachments` 表。

**Q：服务 502 / PM2 显示 errored，日志里几乎没有有用信息？**
几乎都是 `better-sqlite3` **版本漂移**：原生模块与 Node ABI 不匹配时会**段错误**直接崩溃。

```bash
cd <项目目录>
npm run verify:deps                                        # 启动前自检（也可看启动日志的 [deps] 行）
node -e "console.log(require('better-sqlite3/package.json').version)"   # 应为 12.11.1
rm -rf node_modules && npm ci                              # 严格按 lock 文件重装
pm2 restart check-in
```

服务启动时会**自动修复**（见第十七章）；只有在「修复后依然加载不了」时才终止启动。
加固：应用目录写入 `.npmrc`（`save-exact=true`）；必要时以 root 锁定目录
`chattr +i -R node_modules`（下次更新前先 `chattr -i -R node_modules` 解锁）。

**Q：改了 `server/` 下的代码不生效？**
后端改动需**重启服务**（`pm2 restart check-in` 或重新 `npm start`）；前端静态资源刷新即可。

**Q：登录页 / 注册页读取公开状态接口（`/api/settings/public`）返回 401？**
这是路由挂载顺序问题：`routes/activity.js` 与 `routes/checkin.js` 挂载在 `/api` 且自带 `router.use(authRequired)`，
会拦下所有未被更早匹配到的 `/api/*`。因此 `routes/settings.js` 必须在它们**之前**挂载（已在 `server/index.js` 中固定顺序），
且公开接口 `/public` 需注册在设置路由自身的鉴权中间件之前；另外该接口已加入「首次设置」白名单，
未完成首次设置时也能正常读取应用信息与维护态。

**Q：运维者账号登录提示「尚未激活 / 未设置密码」？**
运维者同样不预置密码：请到 `/register.html` 按「姓名 `运维者` + 身份 `运维者`」完成邮箱验证并设密；若忘记密码，服务器执行 `npm run reset-ops` 后用新密码登录。

**Q：注册页提示「未找到可激活的账号」（尤其选「运维者」时）？**
注册**不是自建账号**：服务端必须存在「同名同身份、且从未设过密码」的预置账号才会发码。处理方式：

| 情况 | 处理 |
| --- | --- |
| 账号已激活（有密码） | 直接登录；忘记密码 → `npm run reset-ops` 用新密码登录（强制改密） |
| 姓名与当前预置姓名（OPS_NAME）不一致 | 运行 `npm run config` 修改「运维者预置姓名」，或直接在运维端 / 管理端账号管理里改正；之后重新注册 |
| 账号已注销（隐藏） | 由上一级管理员在账号管理里「恢复」，再重新设密 |
| 身份 / 角色不正确（历史数据） | 运行 `npm run seed` 重新补齐初始数据以修正身份与角色；必要时 `npm run factory-reset` 恢复出厂 |

注：管理端 / 运维者账号**忽略学号**，注册时只需「姓名 + 身份」一致；普通学生才按学号精确匹配。

## 二十、已知说明

- 浏览器无法读取手机 IMEI，系统使用**本地生成并与账号绑定的设备识别码**实现防代签。
- 活动范围坐标为 **GCJ-02**；若设备返回 WGS-84 坐标，可能出现数十至数百米偏移，
  系统已内置坐标系自适应（自动用三种坐标系比对），仍可在 `fences` 表的 `offset_lng / offset_lat` 做统一校准。

- 运维者账号为**运维隔离超管**，可满足任意角色门槛，属预期内的超管能力。
- 出厂重置后，服务启动时**不会**再自动补建默认活动范围（仅全新空库首次初始化才写入）。

## 二十一、自动代管（缺上级自动补位）

**场景**：小班主任还在预备、辅导员尚未就位时，事务全压在班委身上，而班委基线权限不足。
**机制**：某一管理层级**整体没有在岗账号**时，由下级在岗管理岗临时代行其基线权力；上级一注册到岗，权限**自动收回并通知本人**。

### 规则

| 项 | 说明 |
| --- | --- |
| **在岗（可用）** | 未禁用、未注销、且**本人已设置密码**（仅被预置不算） |
| **缺口判定（两层独立）** | 无在岗小班主任 → R2 缺口；无在岗辅导员 → R3 缺口；两层都缺则补到 R3 |
| **补位者** | R2 缺口 → 全部在岗**班委**；R3 缺口 → 优先在岗**小班主任**，无人则由**班委**顶上 |
| **授予范围** | 缺口层级的**全部基线权限**：范围核验、审计日志、终审覆盖、向下授权、账号管理、系统设置、查看数据流，以及 R3 的删除活动与工单审批 |
| **永不授予** | 仅运维者能力（隐私文案、维护开关、7 项运维）、永久拒绝项（查看原始坐标）、学生固有项，以及需显式授予的「查看学生定位」 |
| **收回条件** | 上级**注册设密激活**、邮箱验证码重置密码、上级注销 / 删除 / 清除密码（缺口重现则重新代管）、管理员关闭总开关 |
| **通知** | 开通与收回都通知本人：站内必达，离线 / 闲置超 2 分钟再加邮件（`MAIL_AUTO_COVER_GRANT` / `MAIL_AUTO_COVER_REVOKE`） |
| **开关** | 系统设置「自动代管」，**仅运维者**可切换，默认开启；切换后立即重算 |
| **兜底** | 事件即时触发为主；另有定时巡检（默认 5 分钟，`AUTO_COVER_INTERVAL_MIN` 可调） |
| **安全约束** | 代管所得权限**不可再向下授权**；班委自身基线权限不受影响 |
| **可见性** | 管理端「我的权限」显示「自动代管中」徽标与理由；运维端显示开关与状态卡 |

> 与既有的「辅导员未激活自动委托」（`server/delegate.js`，`source='auto_delegate'`）**并存**：
> 前者针对「辅导员存在但未激活」，受托人是范围内层级最高者；自动代管针对「整层无人在岗」，受托人是在岗班委。
> 两者由自动代管统一编排并去重，不会把同一权限授给两个人。

详细设计与运维排查见本页面上方规则表；相关实现位于 `server/autocover.js`，自动代管总开关在运维端「系统安全」。

### 到岗确认（继承前任 / 代管期间的班级级设置）

班级级设置（通知开关、定位核验等）可能在「上级暂缺、由班委代管」期间被修改。当更高层级的上级（辅导员 / 小班主任）**注册激活到岗**时：

- 系统自动重算自动代管（缺口消除则收回，并通知被收回者）；
- 若该上级层级高于班级级设置的「最后修改者」，或最后修改者已不在岗，则向其推送「**请确认班级设置**」提醒（站内必达，离线 / 不活动时加邮件）；
- 管理端「通知设置」「系统安全」页顶部出现确认条：可「沿用（我知道了）」关闭，或「恢复出厂默认」一键清空所有班级级系统设置（运维者专属键与迁移标记保留）。

班级级设置的「最后修改者」由系统记录（`sys_editor_id` / `sys_editor_at`），每次经 `SYS_SETTINGS` 改写班级级设置（含自动代管开关、定位核验开关、运维端运维开关）都会刷新，可在快照 `sys_editor` 中查看。

- **连线上的文字写明该分支的成立条件**（如「activity_id 为空/非法」「误差超过 200 米」），不使用孤立的「是 / 否」；文字**紧贴它所指向的那个节点**摆放（不放在分叉口），并自动避开所有连线与其它标签，互不遮挡。汇合节点按来源分别标注（如「must_setup=1」→、「首次设置已完成」→）。

## 二十四、官网宣传页（下载站）与配图 / 说明书构建

官网宣传页是一套**纯静态单页站点**（落地页 + 统一下载中心），可独立部署到任意静态托管（与主服务同域的子目录，或独立静态空间）。它由以下文件构成：

- `index.html`：单页官网（深色主题，全幅布局）。含阅读进度条、核心功能 / 可选功能 / 三端介绍 / 界面预览 / 安全与隐私 / 部署指南 / 在线配置演示 / **统一下载中心** / 开源协议等版块；「下载中心」收敛为 **6 个发布文件**：源码包、部署包、服务端包、三端页面包、操作手册包、README（独立下载）。
- `assets/`：官网配图（界面截图）。
- `images/`：备案图标等静态资源。
- `download/`：官网提供的下载文件（6 个发布包）。
- `tui-demo.js`：官网内嵌的终端配置向导演示（仅演示，不读写任何文件）。

> 这套官网静态站**不在应用运行目录内**，而是作为独立发布物随 Release 提供（与可运行的部署包分开）。

配图与说明书构建：

```bash
npm run shots        # 抓取三端真实界面配图，写入 manual-shots/
npm run build:pdf    # 由三册说明书 HTML 生成带封面 / 页码 / 封底的 PDF（manual-*.pdf）
```

> 说明书与官网共用同一套界面配图。`npm run shots` 会先启动服务、写入**完整演示数据**（活动 / 签到 / 请假 / 补签 / 审核 / 消息 / 工单 / 数据流），
> 再以演示账号登录三端、逐项切换菜单并**整页截图**（等待数据加载完成、避免「加载中」等异常态），跑完后自动清理演示数据。
